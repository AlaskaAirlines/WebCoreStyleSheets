# AB#1608258

## Executive Summary

Alaska Air Group brand guidelines prohibit the use of "ligatures" — decorative glyphs that fuse adjacent letter pairs (for example, the joined "fl" in "flight search"). Our shared typography styles were letting browsers render these ligatures by default, which put on-screen text out of compliance with the brand standard across every product using the design system.

This change turns ligatures off for all of the modern typography styles, for every brand theme (Alaska, Alaska Classic, Atmos, and Hawaiian — including the Chronicle Display font). Text now renders with plain, unjoined letters everywhere, bringing the typography back into brand compliance with no other visual change.

Tracking ticket: [AB#1608258](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1608258).

## The Problem

Text rendered through the design system's typography styles was displaying ligatures — connected letter combinations that the browser substitutes automatically for certain pairs like "fl" or "fi". Alaska Air Group's brand guidelines forbid ligatures across all brand typefaces, so any surface using these styles was technically out of brand compliance.

An older rule existed that suppressed *some* ligatures on base page text, but it never reached the newer typography classes that most products actually use, and it only turned off the "common" subset rather than all ligatures. The result was inconsistent, non-compliant text rendering.

## Root Cause

The modern typography classes are generated by two Sass mixins, and neither emitted a `font-variant-ligatures` declaration, so browsers fell back to their default of rendering common ligatures:

- `generate-body-classes` in [_body.scss](../../src/type/partials/_body.scss) — produces the `.body-*` classes.
- `generate-fluid-type-classes` in [_fluid-type.scss](../../src/type/mixins/_fluid-type.scss) — the shared mixin behind the `.display-*`, `.heading-*`, and `.accent-*` classes.

A legacy `font-variant-ligatures: no-common-ligatures` rule lived on the base `html`/`body`/`.baseType` selectors ([_base.scss](../../src/essentials/_base.scss), [_auro-classic.scss](../../src/essentials/legacy/_auro-classic.scss)), but it did not cascade to these generated classes and only suppressed common ligatures — not the full set the brand requires disabled.

## The Fix

The brand ligature policy is defined once, in a shared mixin, and included everywhere the policy must hold — so there is a single source of truth rather than a declaration duplicated per call site:

- [_ligatures.scss](../../src/utilityMixins/_ligatures.scss) — defines `auro_noLigatures`, which emits `font-variant-ligatures: none;`.

That mixin is included in both generator mixins, placed once per generated class rule and outside the CSS-variable / static-fallback `@if/@else` branches so both branches inherit it:

- [_body.scss](../../src/type/partials/_body.scss) — `.body-*`
- [_fluid-type.scss](../../src/type/mixins/_fluid-type.scss) — `.display-*`, `.heading-*`, `.accent-*`

The same mixin also replaced the legacy `font-variant-ligatures: no-common-ligatures` on the base `body`/`.baseType` selectors ([_base.scss](../../src/essentials/_base.scss), [_auro-classic.scss](../../src/essentials/legacy/_auro-classic.scss)), strengthening them to `none` and removing the weaker, contradictory value so the whole system agrees on one policy.

The committed `dist` bundles were regenerated so the rule appears in the shipped typography classes, the base type selectors, and every global theme bundle. A regression test, [typeLigatures.spec.js](../../tests/typeLigatures.spec.js), compiles both real class generators (the CSS-variable and the Alaska static-fallback variants) and asserts every class family emits `font-variant-ligatures: none` and never a ligature-enabling value.

## Why This Works

`font-variant-ligatures: none` disables the *entire* ligature set (common, discretionary, historical, and contextual), which is stronger than the legacy `no-common-ligatures` and is exactly what the brand standard requires.

Because the declaration is emitted directly on the shared, theme-agnostic typography classes — not on any single theme's tokens — it applies regardless of which theme's CSS custom properties are active. That is why one change covers every theme, including the Hawaiian `display` category that uses Chronicle Display. Placing the include outside the `@if/@else` in each mixin guarantees it is present whether a consumer uses the CSS-custom-property build or the static-fallback build.

Routing every call site through the `auro_noLigatures` mixin means the policy is expressed in exactly one place: any future type generator opts in with a single `@include`, and the value can never drift between the generated classes and the base selectors the way the old inline `no-common-ligatures` had.

The change is non-breaking for the typography classes: it introduces one new property with no impact on font family, weight, size, line-height, or letter-spacing. On the base `body`/`.baseType` selectors it changes an existing value from `no-common-ligatures` to `none`, which only widens ligature suppression as the brand standard requires and has no other layout or API effect.

## Outcome

Ligatures no longer render anywhere in the modern typography system, on any brand theme. Text such as "flight search" now displays with separated letters, restoring brand compliance. The change ships in the built stylesheets consumed by all downstream products, and a regression test guards against the rule being dropped in the future. All 72 tests pass and linting is clean.

## Learnings

- Shared typography defaults must set brand-mandated properties explicitly rather than relying on browser defaults; a browser's default of rendering common ligatures silently put text out of compliance.
- Placing a declaration on the shared, theme-agnostic generated classes is the correct altitude for a rule that must hold across every theme — one change covers all themes and any future token generation, without per-theme duplication.
- The legacy base-selector rule (`no-common-ligatures` on `html`/`body`/`.baseType`) gave a false sense of coverage: it neither cascaded to the generated classes nor disabled the full ligature set. When adding a compliance rule, verify it reaches the classes consumers actually apply — and reconcile any weaker legacy rule for the same property so the system does not hold two contradictory values.
- A brand-mandated property that must hold in several places belongs in a single shared mixin (`auro_noLigatures`), not copied inline at each call site. One definition means the value cannot drift and any future generator opts in with a single `@include`.
- A compile-output regression test (compiling the real generators and asserting the emitted CSS) is a durable guard for a declaration that would otherwise be easy to drop during a future refactor.
